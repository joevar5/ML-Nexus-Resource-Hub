## 1. Setup Your Python Environment

### What to run:

```bash
# Step 1: Create an isolated Python environment (so packages don't conflict)
python3 -m venv venv

# Step 2: Activate it — your terminal prompt will change to show (venv)
source venv/bin/activate

# Step 3: Upgrade pip so it can resolve modern packages correctly
pip install --upgrade pip

# Step 4: Install the Prometheus client library for application instrumentation
pip install prometheus-client
```

### → Expected Terminal Output:

```
(venv) your-computer:project-04 you$
```

The `(venv)` prefix confirms you are inside the virtual environment. Every `pip install` and `python` command from now on will use this isolated environment.

### → Expected Output After `pip install`:

```
Successfully installed prometheus-client ...
```

## 2. Start All Infrastructure Services

The monitoring stack needs several services running in the background (Prometheus, Grafana, Elasticsearch, etc.). Docker Compose starts all of them with a single command.

### What to run:

```bash
# Step 1: Copy the environment template
cp .env.example .env

# Step 2: Start all monitoring services
docker-compose up -d
```

The `-d` flag means **detached** — they run in the background, freeing your terminal.

## 3. Deep Dive — Prometheus & Alerting Explained

> **Read this section carefully before running anything.** Understanding Prometheus scrape configuration and alerting rules is the core skill of this project.

### What is Prometheus?

**Prometheus** is a time-series database that **pulls** (scrapes) metrics from your applications at regular intervals. Think of it as a health inspector that visits your services every 15 seconds to collect their vital signs.

```
Application (port 5000)  ←─── scrape ────  Prometheus (port 9090)
     /metrics endpoint                        stores in TSDB
```

- **Pull-based**: Prometheus fetches metrics from your app (not push)
- **Time-series**: Data is stored with timestamps for historical queries
- **Multi-dimensional**: Metrics have labels (method, endpoint, status) for filtering
- **Alerting**: Prometheus evaluates rules and sends alerts to Alertmanager

---

### The file that defines scrape targets: `prometheus/prometheus.yml`

This is the most important file to understand. It tells Prometheus **where to collect metrics from** and **how often**.

**`prometheus/prometheus.yml`** — write this file:

```yaml
# Global settings applied to all scrape jobs
global:
  scrape_interval: 15s          # Collect metrics every 15 seconds
  evaluation_interval: 30s      # Evaluate alert rules every 30 seconds
  external_labels:
    monitor: 'ml-monitoring'

# Alertmanager configuration
alerting:
  alertmanagers:
    - static_configs:
        - targets:
            - alertmanager:9093

# Alert rule files
rule_files:
  - 'alerts.yml'

# Scrape targets — where Prometheus collects metrics from
scrape_configs:
  # ── Self-monitoring: Prometheus scrapes its own metrics ──────────
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']

  # ── Infrastructure metrics from Node Exporter ─────────────────────
  - job_name: 'node-exporter'
    static_configs:
      - targets: ['node-exporter:9100']

  # ── Application metrics from your ML API ──────────────────────────
  - job_name: 'ml-api'
    static_configs:
      - targets: ['ml-api:5000']
    metrics_path: /metrics

  # ── ML Model metrics (if separate from API) ───────────────────────
  - job_name: 'ml-model'
    static_configs:
      - targets: ['ml-api:8000']
    metrics_path: /metrics
```

---

### How Prometheus reads metrics from your application

In your `src/instrumentation.py`, you expose metrics like this:

```python
from prometheus_client import Counter, Histogram, Gauge, generate_latest

# Define metrics
http_requests_total = Counter(
    'http_requests_total',
    'Total HTTP requests',
    ['method', 'endpoint', 'status']
)

http_request_duration_seconds = Histogram(
    'http_request_duration_seconds',
    'HTTP request duration in seconds',
    ['method', 'endpoint'],
    buckets=[0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0]
)

active_connections = Gauge(
    'active_connections',
    'Current active connections'
)

# Expose metrics endpoint
@app.route('/metrics')
def metrics():
    return generate_latest()
```

When Prometheus scrapes `http://ml-api:5000/metrics`, it receives:

```
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",endpoint="/predict",status="200"} 12345
http_requests_total{method="POST",endpoint="/predict",status="500"} 3

# HELP http_request_duration_seconds HTTP request duration in seconds
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{method="GET",endpoint="/predict",le="0.1"} 9500
http_request_duration_seconds_bucket{method="GET",endpoint="/predict",le="0.5"} 12000

# HELP active_connections Current active connections
# TYPE active_connections gauge
active_connections 42
```

### What metrics look like in Prometheus

After Prometheus has been scraping for a few minutes, you can query metrics:

```bash
# Query: How many requests per second is the API handling?
curl 'http://localhost:9090/api/v1/query?query=rate(http_requests_total[5m])'
```

### → Expected Output:

```json
{
  "status": "success",
  "data": {
    "result": [
      {
        "metric": {"method": "GET", "endpoint": "/predict", "status": "200"},
        "value": [1697635200, "12.5"]
      }
    ]
  }
}
```

This means the API is handling **12.5 requests per second** for `GET /predict` with status 200.

## 4. Configure Prometheus Scrape Targets

### Add your application as a scrape target

If your ML application is running on a different port or host, add it to `prometheus/prometheus.yml`:

```yaml
scrape_configs:
  # Add your custom application
  - job_name: 'my-ml-app'
    static_configs:
      - targets: ['my-app-host:5000']
    metrics_path: /metrics
    scrape_interval: 15s
```

### Reload Prometheus configuration without restart:

```bash
# Prometheus supports hot-reload via HTTP POST
curl -X POST http://localhost:9090/-/reload
```

### → Expected Output:

```
# No output means success — Prometheus reloaded its config
```

### Verify the new target appears:

Go to **`http://localhost:9090/targets`** — your new target should appear in the list.

### Create your first dashboard (Infrastructure Dashboard):

1. Click **+ → Dashboard** in the left sidebar
2. Click **Add a new panel**

   ```promql
   100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
   ```

4. Set **Panel Title** to "CPU Usage (%)"
5. Set **Visualization** to "Time Series"
6. Click **Apply** in the top right

### → Expected Output:

You should see a real-time graph showing your CPU usage percentage over time, updating every 15 seconds.

### Add more panels:

**Memory Usage:**
```promql
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100
```

**Disk Usage:**
```promql
(node_filesystem_size_bytes{mountpoint="/"} - node_filesystem_avail_bytes{mountpoint="/"}) / node_filesystem_size_bytes{mountpoint="/"} * 100
```

**Network Traffic:**
```promql
rate(node_network_receive_bytes_total[5m])
```

## 6. Set Up Alerting Rules

Alerting rules tell Prometheus **when to trigger alerts**. They are defined in `prometheus/alerts.yml`.

### The alerting rules file: `prometheus/alerts.yml`

**`prometheus/alerts.yml`** — write this file:

```yaml
groups:
  # ── Infrastructure Alerts ──────────────────────────────────────────
  - name: infrastructure
    rules:
      # Alert: High CPU Usage
      - alert: HighCpuUsage
        expr: 100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 80
        for: 5m
        labels:
          severity: warning
          service: infrastructure
        annotations:
          summary: "High CPU usage on {{ $labels.instance }}"
          description: "CPU usage is {{ $value | printf "%.1f" }}% (threshold: 80%)"
          runbook_url: "https://runbooks/target-down"

      # Alert: High Memory Usage
      - alert: HighMemoryUsage
        expr: (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100 > 85
        for: 5m
        labels:
          severity: warning
          service: infrastructure
        annotations:
          summary: "High memory usage on {{ $labels.instance }}"
          description: "Memory usage is {{ $value | printf "%.1f" }}% (threshold: 85%)"

      # Alert: Low Disk Space
      - alert: LowDiskSpace
        expr: (node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) * 100 < 15
        for: 2m
        labels:
          severity: critical
          service: infrastructure
        annotations:
          summary: "Low disk space on {{ $labels.instance }}"
          description: "Only {{ $value | printf "%.1f" }}% disk space remaining"

      # Alert: Service Down
      - alert: ServiceDown
        expr: up == 0
        for: 2m
        labels:
          severity: critical
          service: infrastructure
        annotations:
          summary: "Service {{ $labels.job }} is down"
          description: "{{ $labels.instance }} has been down for 2 minutes"

  # ── Application Alerts ────────────────────────────────────────────
  - name: application
    rules:
      # Alert: High Error Rate
      - alert: HighErrorRate
        expr: |
          rate(http_requests_total{status=~"5.."}[5m])
          / rate(http_requests_total[5m]) > 0.05
        for: 5m
        labels:
          severity: critical
          service: application
        annotations:
          summary: "High error rate detected"
          description: "Error rate is {{ $value | humanizePercentage }} (threshold: 5%)"
          runbook_url: "https://runbooks/high-error-rate"

      # Alert: High Latency
      - alert: HighLatency
        expr: histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m])) > 1
        for: 5m
        labels:
          severity: warning
          service: application
        annotations:
          summary: "High P95 latency detected"
          description: "P95 latency is {{ $value | humanizeDuration }} (threshold: 1s)"

  # ── ML Model Alerts ───────────────────────────────────────────────
  - name: ml_model
    rules:
      # Alert: Model Accuracy Drop
      - alert: ModelAccuracyDrop
        expr: model_accuracy < 0.85
        for: 10m
        labels:
          severity: critical
          service: ml
        annotations:
          summary: "Model accuracy dropped below 85%"
          description: "Current accuracy: {{ $value | humanizePercentage }}"
          runbook_url: "https://runbooks/model-drift"

      # Alert: Data Drift Detected
      - alert: DataDriftDetected
        expr: data_drift_score > 0.5
        for: 5m
        labels:
          severity: warning
          service: ml
        annotations:
          summary: "Data drift detected on {{ $labels.feature }}"
          description: "Drift score: {{ $value | printf "%.2f" }} (threshold: 0.5)"

      # Alert: High Inference Latency
      - alert: HighInferenceLatency
        expr: histogram_quantile(0.99, rate(model_inference_duration_seconds_bucket[5m])) > 0.5
        for: 5m
        labels:
          severity: warning
          service: ml
        annotations:
          summary: "High inference latency (P99 > 500ms)"
          description: "P99 inference latency: {{ $value | humanizeDuration }}"
```

---

### How alert rules work

Each alert rule has these key parts:

```
- alert: HighErrorRate          ← name of the alert
  expr: <PromQL query>           ← condition that triggers the alert
  for: 5m                        ← how long the condition must be true before firing
  labels:
    severity: critical           ← used by Alertmanager for routing
  annotations:
    summary: "..."               ← short description shown in notification
    description: "..."           ← detailed info with current value
    runbook_url: "..."           ← link to on-call runbook
```

The `for: 5m` means: "Only fire this alert if the condition has been true for **5 consecutive minutes**." This prevents flapping — momentary spikes won't trigger alerts.

## 8. View Logs in Kibana

Kibana is the **log visualization** tool — it lets you search and analyze logs collected by Filebeat and Logstash.

### Access the Kibana UI:

1. Open **`http://localhost:5601`** in your browser
2. If prompted for login, use `elastic` / your configured password

### Create an index pattern (first time only):

1. Go to **Management → Stack Management → Index Patterns**
2. Click **Create index pattern**
3. Enter pattern: `logs-*`
4. Select `@timestamp` as the time field
5. Click **Create index pattern**

### → Expected Output:

```
Index pattern: logs-*
Time field: @timestamp
Fields discovered: 15
```

### Search for error logs:

1. Go to **Discover** in the left sidebar
2. In the search bar, enter:
   ```
   level:ERROR
   ```
3. Set the time range to "Last 15 minutes"
4. You should see all error-level log entries

### → Expected Output:

```
Time                    Level    Message
2025-10-18 14:32:10     ERROR    Failed to load model: FileNotFound
2025-10-18 14:33:45     ERROR    Database connection failed
2025-10-18 14:35:12     ERROR    Request timeout after 30s
```

### Search for slow requests:

In the search bar, enter:
```
duration_ms:>1000
```

This shows all log entries where the request took more than 1 second.

### Create a log analysis dashboard:

1. Go to **Dashboard** in the left sidebar
2. Click **Create new dashboard**
3. Add visualizations:
   - **Log volume over time** (Vertical Bar chart, Y-axis: Count, X-axis: @timestamp)
   - **Log levels distribution** (Pie chart, Slice by: level)
   - **Top error messages** (Data table, Split by: message, Metric: Count)
