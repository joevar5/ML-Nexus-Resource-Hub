## 1. Setup Your Python Environment

### What to run:

```bash
# Step 1: Create an isolated Python environment (so packages don't conflict)
python3 -m venv venv

# Step 2: Activate it — your terminal prompt will change to show (venv)
source venv/bin/activate

# Step 3: Upgrade pip so it can resolve modern packages correctly
pip install --upgrade pip

# Step 4: Install all project dependencies
pip install -r src/requirements.txt
```

### → Expected Terminal Output:

```
(venv) your-computer:project-03 you$
```

The `(venv)` prefix confirms you are inside the virtual environment. Every `pip install` and `python` command from now on will use this isolated environment.

### → Expected Output After `pip install`:

```
Successfully installed dvc mlflow torch torchvision great-expectations apache-airflow ...
```

## 2. Start All Infrastructure Services

The pipeline needs several services running in the background (database, storage, experiment tracker, etc.). Docker Compose starts all of them with a single command.

### What to run:

```bash
docker-compose -f dvc/docker-compose.yml up -d
```

The `-d` flag means **detached** — they run in the background, freeing your terminal.

## 3. Deep Dive — DVC DAGs Explained

> **Read this section carefully before running anything.** Understanding DVC DAGs is the core skill of this project.

### What is a DVC DAG?

A **DAG** = **D**irected **A**cyclic **G**raph.

Think of it as a **recipe with steps that depend on each other**:

```
Ingest Data  →  Validate Data  →  Preprocess  →  Train Model  →  Evaluate
```

- **Directed**: each step feeds into the next (data flows in one direction)
- **Acyclic**: no loops — a step cannot depend on itself or a future step
- **Graph**: it's not just a list; some steps can run in parallel if they don't depend on each other

DVC turns this recipe into **cached, reproducible pipeline stages**. If you only change the training code, DVC will **skip** the ingestion and preprocessing steps and jump straight to training — because the inputs haven't changed.

---

### The file that defines the DAG: `dvc/dvc.yaml`

This is the most important file to understand. Here is what it looks like and what every line means:

**`dvc/dvc.yaml`** — write this file:

```yaml
stages:

  # ── STAGE 1: Load raw data from CSV / API / database ──────────────────────
  ingest:
    cmd: python -m src.data_ingestion --output data/raw      # command to run
    deps:                                                    # inputs DVC tracks
      - src/data_ingestion.py                               #   if this script changes → re-run
    outs:                                                    # outputs DVC caches
      - data/raw/dataset.csv                                #   cached so next stages can reuse

  # ── STAGE 2: Validate data quality with Great Expectations ────────────────
  validate:
    cmd: python -m great_expectations.cli.cli checkpoint run training_data_checkpoint
    deps:
      - data/raw/dataset.csv                               # depends on output of stage 1
      - great_expectations/expectations/training_data_suite.json
    outs:
      - great_expectations/uncommitted/data_docs/local_site/index.html

  # ── STAGE 3: Clean, encode, and split data ────────────────────────────────
  preprocess:
    cmd: python -m src.preprocessing --input data/raw --output data/processed
    deps:
      - src/preprocessing.py
      - data/raw/dataset.csv                               # depends on stage 1 output
    params:                                                # reads values from params.yaml
      - preprocessing.test_size
      - preprocessing.random_seed
    outs:
      - data/processed/train.csv
      - data/processed/val.csv
      - data/processed/test.csv
      - artifacts/label_encoder.pkl

  # ── STAGE 4: Train the PyTorch model ──────────────────────────────────────
  train:
    cmd: python -m src.training --train data/processed/train.csv --val data/processed/val.csv --output models/current
    deps:
      - src/training.py
      - data/processed/train.csv                          # depends on stage 3 output
      - data/processed/val.csv
    params:                                               # reads values from params.yaml
      - training.learning_rate
      - training.batch_size
      - training.num_epochs
      - training.model_name
    outs:
      - models/current/best_model.pth
    metrics:
      - metrics/train_metrics.json:                      # DVC tracks these as metrics
          cache: false

  # ── STAGE 5: Evaluate the trained model ───────────────────────────────────
  evaluate:
    cmd: python -m src.evaluation --model models/current/best_model.pth --test data/processed/test.csv
    deps:
      - src/evaluation.py
      - models/current/best_model.pth                    # depends on stage 4 output
      - data/processed/test.csv
    outs:
      - reports/confusion_matrix.png
      - reports/classification_report.txt
    metrics:
      - metrics/eval_metrics.json:
          cache: false
```

---

### The parameters file: `dvc/params.yaml`

This is where you store all tunable values so you **don't hard-code them** inside Python scripts. When you change a param, DVC detects the change and re-runs only the affected stages.

**`dvc/params.yaml`** — write this file:

```yaml
preprocessing:
  test_size: 0.2          # 20% of data goes to test set
  val_size: 0.1           # 10% goes to validation set
  random_seed: 42         # makes splits reproducible

training:
  model_name: resnet18    # options: resnet18, mobilenet_v2
  num_epochs: 20
  batch_size: 32
  learning_rate: 0.001
  patience: 5             # stop training if val_acc doesn't improve for 5 epochs

evaluation:
  threshold: 0.80         # minimum accuracy to promote model to Staging
```

---

### How DVC reads params from your Python code

In your `src/training.py`, you read params like this instead of hard-coding values:

```python
import dvc.api

# DVC automatically injects params from params.yaml
params = dvc.api.params_show()

learning_rate = params["training"]["learning_rate"]   # → 0.001
batch_size    = params["training"]["batch_size"]      # → 32
num_epochs    = params["training"]["num_epochs"]      # → 20
model_name    = params["training"]["model_name"]      # → "resnet18"
```

### → Expected Output:

```
         +--------+
         | ingest |
         +--------+
              *
              *
              *
        +----------+
        | validate |
        +----------+
              *
              *
              *
       +------------+

       +------------+
              *

         +-------+
```

Each box is a **stage**. The `*` lines show **dependencies** — data flowing downward from one stage to the next.

> **If your `dvc dag` output doesn't match this**, check that `dvc/dvc.yaml` is saved correctly and run `dvc dag` from the project root directory (not inside the `dvc/` folder).

### What DVC caches look like on disk

After you run the pipeline once, DVC creates a `.dvc/cache/` folder:

```
.dvc/
├── cache/
│   ├── files/
│   │   └── md5/
│   │       ├── 3a/
│   │       │   └── f8c9d2e1...  ← cached copy of data/raw/dataset.csv
│   │       └── 7b/
│   │           └── 2e4f1a9c...  ← cached copy of data/processed/train.csv
└── config                       ← tells DVC where the remote storage is (MinIO)
```

When you run `dvc repro` a second time without changing anything:

```
Stage 'ingest' didn't change, skipping
Stage 'validate' didn't change, skipping
Stage 'preprocess' didn't change, skipping
Stage 'train' didn't change, skipping
Stage 'evaluate' didn't change, skipping
Data and pipelines are up to date.
```

This is the **superpower of DVC** — it never wastes time re-running stages whose inputs haven't changed.

## 4. Run the Pipeline Step by Step via DVC

Now that you understand the DAG, let's run it.

```bash

dvc init

# Tell DVC to use MinIO as the remote storage (where it pushes cached data)

dvc remote modify minio endpointurl http://localhost:9000
dvc remote modify minio access_key_id minioadmin
dvc remote modify minio secret_access_key minioadmin
```

## 5. Initialize and Use Apache Airflow

Airflow is the **scheduler** — it runs the DVC pipeline automatically on a schedule (e.g. nightly) or when triggered.

### Initialize the Airflow database (first time only):

```bash
docker-compose -f dvc/docker-compose.yml exec airflow-webserver airflow db init
```

### Create your admin login:

```bash
docker-compose -f dvc/docker-compose.yml exec airflow-webserver airflow users create \
    --username admin \
    --password admin \
    --firstname Admin \
    --lastname User \
    --role Admin \
    --email admin@example.com
```

**→ Expected Output:**
```
[2025-10-18] INFO - User "admin" created with role "Admin"
```

### What the DAG file looks like

**`dags/ml_pipeline_dag.py`** — this is what Airflow reads:

```python
from airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime, timedelta

# Default settings applied to every task
default_args = {
    "owner": "ml-team",
    "retries": 2,                           # retry failed tasks twice
    "retry_delay": timedelta(minutes=5),    # wait 5 min between retries
    "email_on_failure": True,
    "email": ["ml-alerts@yourteam.com"],
}

with DAG(
    dag_id="ml_training_pipeline",
    default_args=default_args,
    description="End-to-end ML training pipeline",
    schedule_interval="0 2 * * *",          # runs every night at 2:00 AM
    start_date=datetime(2025, 10, 1),
    catchup=False,                          # don't backfill missed runs
    tags=["ml", "training", "dvc"],
) as dag:

    # Each task wraps a DVC stage command
    ingest = BashOperator(
        task_id="ingest_data",
        bash_command="cd /opt/ml-pipeline && dvc repro ingest",
    )

    validate = BashOperator(
        task_id="validate_data",
        bash_command="cd /opt/ml-pipeline && dvc repro validate",
    )

    preprocess = BashOperator(
        task_id="preprocess_data",
        bash_command="cd /opt/ml-pipeline && dvc repro preprocess",
    )

    train = BashOperator(
        task_id="train_model",
        bash_command="cd /opt/ml-pipeline && dvc repro train",
    )

    evaluate = BashOperator(
        task_id="evaluate_model",
        bash_command="cd /opt/ml-pipeline && dvc repro evaluate",
    )

    # This line sets the execution ORDER: ingest → validate → preprocess → train → evaluate
    ingest >> validate >> preprocess >> train >> evaluate
```

> **Key line:** `ingest >> validate >> preprocess >> train >> evaluate`
> This is Airflow's syntax for "run these tasks in this order". The `>>` operator chains tasks into a DAG, exactly mirroring the DVC DAG.

### Access the Airflow UI:

1. Open **`http://localhost:8080`** in your browser
2. Log in with `admin` / `admin`
3. Find **`ml_training_pipeline`** in the DAG list
4. Toggle the switch on the left to **Active** (it's paused by default)
5. Click the **▶ Play** button → **Trigger DAG** to run it immediately

## 6. Configure the MinIO Storage Bucket

MinIO is the **object storage** — it stores trained model files, plots, and MLflow artifacts.

1. Open **`http://localhost:9001`** in your browser
2. Login:
   - **Access Key**: `minioadmin`
   - **Secret Key**: `minioadmin`
3. Click **Buckets** in the left sidebar
4. Click **+ Create Bucket**
5. Type `mlflow` as the bucket name → click **Create Bucket**

> **Why `mlflow`?** The MLflow container is pre-configured with `--default-artifact-root s3://mlflow/`. Any model files, plots, or logs that MLflow saves will go into this bucket automatically.

## 7. View Results in MLflow

Every training run is automatically logged to MLflow by `src/training.py`. Here's how to explore the results.

### Access the MLflow UI:

Open **`http://localhost:5000`** in your browser.

### What you'll see:

```
Experiments
└── image_classification              ← your experiment name
    ├── resnet18_run_001              ← one row per training run
    │   ├── Parameters
    │   │   ├── learning_rate: 0.001
    │   │   ├── batch_size: 32
    │   │   ├── num_epochs: 20
    │   │   └── model_name: resnet18
    │   ├── Metrics
    │   │   ├── train_loss: 0.312
    │   │   ├── train_accuracy: 0.912
    │   │   ├── val_accuracy: 0.889
    │   │   └── test_accuracy: 0.884
    │   └── Artifacts
    │       ├── model/               ← saved PyTorch model
    │       ├── plots/
    │       │   └── confusion_matrix.png
    │       └── classification_report.txt
    └── mobilenet_run_001            ← compare against a different architecture
```

### How to compare two runs:

1. Check the boxes next to two runs
2. Click **Compare** at the top
3. MLflow shows a side-by-side metric comparison and overlapping loss curves

### How to register the best model for production:

1. Open a run → click **Register Model**
2. Name it `image_classifier`
3. In the **Model Registry** tab, find your model → click **Stage: None** → change to **Staging**
4. After manual review → change **Staging** → **Production**
